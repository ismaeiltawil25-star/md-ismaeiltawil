# Architecture Guidelines - Reinforcement Control Loop

## Overview
The project follows a **Reinforcement Control Loop** architecture designed to make the system highly maintainable, resilient against technical debt, and ready for safe evolution. This design philosophy is implemented through strict **Single Responsibility Principle (SRP)** compliance at every level.

## Core Philosophy: SRP-First Design
Each component in the system has **one, and only one, reason to change**. Complex operations are decomposed into a pipeline of discrete, testable, and interchangeable processing units.

## The Processing Pipeline (Control Loop)
The transformation of a Markdown document to a styled HTML string is no longer a monolithic process. It is a controlled pipeline with explicit stages, each guarded by error handling and performance monitoring.

```
User Input → [Parsing] → [Wrapping] → [Normalization] → [RTL Processing] → [Task List Fix] → Output
                 ↑              ↑                 ↑                ↑                  ↑
                 └────────── ErrorLogger & PerformanceMonitor ───────────────────────┘
```

### 1. Input Validation & Preparation
- **Unit**: `DocumentLoader`
- **Responsibility**: Validate file existence, size guard (10 MB limit), and basic encoding.
- **Output**: A `MarkdownDocument` data object or a clear `Result::errorMessage`.

### 2. Preprocessing
- **Unit**: `MarkdownPreprocessor`
- **Responsibility**: Strip YAML front-matter, convert definition lists.
- **Output**: Clean Markdown string.

### 3. HTML Rendering
- **Unit**: `MarkdownHtmlRenderer`
- **Responsibility**: Orchestrate the pipeline. Call `md4c` for the initial raw HTML, then pass the result sequentially through the specific wrappers and normalizers.
- **Current Monitoring**: `MarkdownHtmlRenderer::render()` is timed as a top-level operation using `PerformanceMonitor`. Individual post-processing stages are not yet timed separately; per-stage diagnostics are planned in the stabilization roadmap.

### 4. Element Wrapping (Visual Styling)
- **Units**: `HtmlElementWrapper`
- **Responsibility**: Wrap specific HTML structures (like `<pre><code>` or `<blockquote>`) into table-based layouts to allow `QTextDocument` to render backgrounds and borders reliably.
- **Key**: This is a pure transformation function. It takes HTML and returns HTML.

### 5. HTML Normalization
- **Unit**: `HtmlNormalizer`
- **Responsibility**: Replace raw HTML5 tags (like `<kbd>`, `<mark>`) with equivalent, styleable `QTextDocument`-friendly markup. Strip unsupported interactive elements (like `<details>`).
- **Key**: Isolates the quirks and limitations of the specific rendering engine (`QTextDocument`).

### 6. RTL Direction Processing
- **Unit**: `HtmlRtlProcessor`
- **Responsibility**: Scan block-level elements for Arabic (or other RTL) text and inject `dir="rtl"` and `align="right"` attributes.
- **Key**: Complex logic for finding matching closing tags and avoiding nested structures (like code blocks) is perfectly isolated here.

### 7. Task List Normalization
- **Unit**: `TaskListNormalizer`
- **Responsibility**: Convert HTML checkbox inputs (generated by `md4c`) into static Unicode characters (☑, ☐) because `QTextDocument` does not support interactive checkboxes.
- **Key**: Handles a very specific rendering limitation of the target framework.

## Reinforcement Control Loop
To ensure the system does not accumulate technical debt, the architecture is built around three reinforcing controls:

1.  **ErrorLogger (Centralized Error Handling)**
    *   Current implemented logging covers `DocumentLoader` failures/warnings and `MarkdownHtmlRenderer` md4c failures.
    *   HTML post-processing stages currently return transformed strings and do not yet emit per-stage warnings or errors.
    *   Provides a single point of control for log levels, filtering, and formatting.
    *   The stabilization roadmap keeps this as the intended direction, but full per-stage render diagnostics are not implemented yet.

2.  **PerformanceMonitor (Performance Agent)**
    *   Currently wraps the top-level Markdown render operation.
    *   Future stabilization work should add cheap per-stage timing for loading, preprocessing, md4c rendering, normalization, RTL processing, and appearance reapplication.
    *   Logs operations that exceed a certain threshold (e.g., 100ms).
    *   Detects performance regressions early, preventing "slow code" from becoming a hidden debt.

3.  **Static Analysis & Automated Testing (CI/CD Gate)**
    *   The modular structure makes mocking and unit testing trivial.
    *   Each unit can be tested in isolation (e.g., `HtmlRtlProcessor` can be tested with a static HTML string).
    *   CI must enforce build success and passing tests before allowing changes to `main`.

## Directory Structure
To enforce the physical separation of concerns, the `src` directory is organized as follows:

```
src/
├── app/                  # UI layer (MainWindow, Dialogs)
│   ├── appearance/       # Appearance settings (separate concern)
│   ├── MainWindow.h/.cpp
│   └── ...
├── models/               # Data structures (e.g., MarkdownDocument)
├── services/             # Business logic without UI (DocumentLoader, Preprocessor)
├── renderers/            # HTML processing pipeline (The new units)
│   ├── MarkdownHtmlRenderer.h/.cpp
│   ├── HtmlElementWrapper.h/.cpp
│   ├── HtmlNormalizer.h/.cpp
│   ├── HtmlRtlProcessor.h/.cpp
│   └── TaskListNormalizer.h/.cpp
└── utils/                # Cross-cutting concerns (ErrorLogger, PerformanceMonitor)
    ├── ErrorLogger.h/.cpp
    └── PerformanceMonitor.h/.cpp
```

## Future Evolution
This architecture makes it trivial to:
*   **Add a new processor**: Create `NewProcessor.h/.cpp`, implement a `static QString process(const QString &html)` method, and insert it into the pipeline in `MarkdownHtmlRenderer::render()`.
*   **Replace an engine**: Swap `md4c` for another parser without touching the rest of the application.
*   **Optimize a bottleneck**: Profile `PerformanceMonitor` output to identify slow units, optimize them, and verify with isolated unit tests.
